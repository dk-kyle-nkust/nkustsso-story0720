# SSO 登入續期與系統整合需求紀錄

紀錄日期：2026-10-13。

狀態：已實作中央 1 小時滑動續期。使用者已更正最長連續登入為 **4 小時**，不是先前建議的 8 小時。接收系統透過 OIDC 等登入流程觸發續期。正式環境整合、容量驗證與跨系統立即登出仍待辦。

## 使用者希望達到的目標

- 兼顧資訊安全與使用便利，減少使用者重複輸入帳密。
- 使用者進入其他系統後，不必手動回到 SSO 首頁才能繼續登入。
- 盡量沿用標準 OIDC 登入流程，降低各系統的改動幅度，避免重寫業務功能。
- 管理者終止登入、帳號停用及到期限制仍須有效，不能被自動續期繞過。
- 延續 ASP.NET Core、linq2db 與伺服器端 Session 架構，不使用 Entity Framework。

## 目前實作的行為

| 項目 | 現況 |
| --- | --- |
| 中央登入 | 資料庫儲存 Session，瀏覽器 Cookie 攜帶受保護的 Session 參照 |
| 中央期限 | 1 小時滑動窗口，首次登入起算最多 4 小時 |
| 接收系統 | 各自使用獨立 Cookie，期限由各系統設定 |
| 再次驗證 | 各系統登入到期後，下次存取受保護頁面會觸發 OIDC，導向 SSO |
| SSO 仍有效 | 免重新輸入帳密，完成驗證後返回原系統 |
| SSO 已失效 | 要求重新輸入帳密，成功後建立新的中央 Session |
| 自動續期／心跳 | 已加入符合條件的 SSO 請求續期；未加入背景保活心跳 |
| 跨系統立即登出 | 尚未加入；中央撤銷不會立即使下游既有 Cookie 失效 |

離開 SSO 首頁不會刪除中央 Cookie 或 Session。需要驗證時，瀏覽器會在導向 SSO 的過程中自動帶上 SSO Cookie；各系統不需要讀取或共用中央 Cookie。

這個流程是「各系統 → SSO 驗證端點 → 返回原系統」，不要求使用者停留在 SSO 首頁，也不是每次都必須看到帳密輸入畫面。

## 滑動到期的意思

Session 尚未失效時，符合條件的中央驗證請求可將期限向後延長。延長的是現有 Session 的有效期限，不必每次建立新的登入紀錄。

例如續期窗口為 1 小時：10:00 登入，原本 11:00 到期；10:40 再次存取 SSO 並符合續期條件，便可延長至 11:40。若沒有再續期，就在 11:40 到期。

只有操作各系統自己的頁面，不代表有存取 SSO。滑動到期不能讓中央自動知道所有下游活動；仍需要各系統既有或新增的 OIDC 重新驗證流程。

「有活動才續期」在此是指符合規則的 SSO 請求，不代表 SSO 能辨識使用者是否真的正在操作鍵盤或滑鼠。背景輪詢也可能產生請求，因此不以固定背景心跳作為預設方案。

## 已實作方案：中央滑動續期，加上最長登入期限

以下為目前原型設定。正式環境仍須依校方政策與系統風險確認。

| 設定 | 目前行為 |
| --- | --- |
| 中央續期窗口 | 1 小時 |
| 續期時機 | 剩餘期限不超過 30 分鐘時，符合條件的 SSO 導向或頁面瀏覽；不必每個請求都更新 |
| 最長連續登入時間 | 4 小時，自最初登入時間起算，續期不得重設此時間 |
| 下游重新驗證 | 使用 OIDC 等登入流程；本地登入期限由接收系統設定 |
| 到期或被撤銷 | 不允許續期，須重新登入；帳號停用或鎖定時仍拒絕登入 |

中央透過 Cookie Authentication 的 `ITicketStore` 同步處理登入票證、瀏覽器 Cookie 的重新發送及資料庫 Session 期限，不只延長瀏覽器 Cookie。新期限取「本次續期時間＋續期窗口」與「最初登入時間＋最長期限」兩者較早者。瀏覽器仍使用非持久登入 Cookie，實際期限由伺服器 Session 檢查。

續期適用於 GET `/`、`/integration`、`/connect/authorize`、`/ticket/authorize`，以及 `/admin/sessions`、`/admin/tickets`、`/admin/systems` 及其子路徑；回應狀態 400 以上不續期。瀏覽器有提供 `Sec-Fetch-Dest` 時，僅接受 `document` 導向，不替 `fetch` 或 iframe 續期；沒有此標頭的相容用戶端仍可使用。此標頭不是裝置身分證明，不能防止持有有效 Cookie 者自行製造請求。健康檢查、token exchange 及其他路徑不延長中央登入。

設定檔為 `NkustSso.Server/appsettings.json` 的 `Sso:Session`：`WindowMinutes=60`、`MaximumMinutes=240`。管理頁會同時顯示目前到期時間與最晚重新登入時間。原 `CreatedAt` 保持不變，無需新增資料表欄位。

續期前須檢查中央 Session、帳號啟用／鎖定狀態及 SecurityStamp。更新需具備並行保護，避免管理者剛撤銷登入，另一個稍晚完成的續期請求又將它恢復。

最長期限是中央 Session 的上限。若下游不額外檢查，它既有的本地登入仍可能延續到自己的期限；不可把中央上限宣稱為全系統立即停止操作的保證。

## 各系統需要調整多少

| 系統現況 | 預期配合範圍 |
| --- | --- |
| 已串接 OIDC，登入到期會重新導向 SSO | 通常可沿用流程，檢查期限設定即可；未必需要新增程式碼 |
| 本地 Cookie 持續滑動延長，長時間不再聯絡 SSO | 需限制本地登入期限，或加入有界限的 OIDC 重新驗證機制 |
| 尚未串接 SSO 的系統 | 仍須先完成 OIDC 或其他相容登入整合 |
| 舊 ASP／DLL 系統 | 需盤點現有登入與 Session 機制，不能預先保證只改設定即可 |

接收系統應設定有限的本地登入期限，並於需要重新驗證時導向中央 SSO，作為續期觸發點；正式接入仍須逐一確認各系統的配合方式。

下游驗證間隔應短於中央續期窗口。若使用者久未操作，等再次導向時中央 Session 已到期，就仍須重新輸入帳密。若系統長時間只在前端編輯、沒有觸發登入驗證，也不能保證中央一直有效。

各系統的帳號對應與功能權限仍由各系統管理，不因加入中央續期而改為共用全部業務權限。

## 使用體驗與實作界線

- 優先沿用瀏覽器正常 OIDC 導向，不以共用 Cookie、交換使用者密碼或隱藏 iframe 作為預設整合方式。
- 正常導向可能短暫切換網址；「不用手動回首頁」不等於完全沒有導向。
- 重新驗證後返回安全的原系統網址，維持既有 redirect URI、state、nonce 與 PKCE 驗證。
- 表單尚未送出時避免突然導向造成資料遺失；需要保存草稿或在適當操作時提示重新登入。
- API／AJAX 登入失效應由系統妥善處理，不把登入頁 HTML 當作 API 結果，也不自動重送可能產生副作用的操作。
- 不加入無人操作也一直執行的保活心跳，避免閒置頁面永久續期。

## 管理者終止登入的範圍

| 操作 | 影響 |
| --- | --- |
| 終止此登入 | 終止所選的一筆中央 Session，例如某個瀏覽器設定檔的登入；其他獨立登入仍保留 |
| 終止此帳號所有登入 | 終止該帳號當下所有有效中央 Session，不影響其他帳號 |
| 停用帳號 | 拒絕該帳號建立新的中央登入；與單純終止 Session 不同 |

同一個瀏覽器設定檔的多個分頁通常共用 Cookie，因此「此登入」不是只終止一個分頁。

終止 Session 不會永久禁止登入；帳號仍有效時，使用者可重新輸入帳密登入。滑動續期不能恢復已被終止的 Session。

目前中央終止後，各系統既有登入仍可操作到自己的到期時間。生效延遲取決於各系統本地登入的剩餘期限。若未來要求各系統立即停止操作，需另設計 back-channel logout 或中央狀態檢查，並讓各系統配合，不屬於單純滑動續期。

## 已驗證與正式環境待辦

隔離測試使用真實 ASP.NET Core Cookie 處理器與可控制的時鐘，驗證未達門檻不續期、符合門檻可續期、跨越原始 1 小時期限、4 小時上限、背景請求不延長、請求中撤銷優先及到期後重新登入。瀏覽器測試驗證 OIDC 續期、跨兩個系統登入、管理操作、停用與權限限制。

正式環境仍需：

1. 確認正式系統可接受的中央撤銷生效延遲，以及是否需要敏感操作重新驗證。
2. 逐一盤點本地登入期限與 OIDC 行為，判斷哪些只需設定調整、哪些需修改登入整合。
3. 針對真正的業務表單與 API 驗證資料保存、返回原頁面及避免副作用重送；Server 隔離測試不能取代各系統驗收。
4. 接上正式帳號來源、資料庫、TLS、持久簽章／加密金鑰，完成容量與安全測試；目前仍為 Development 原型。

## 容量與重複登入的資源成本

使用者提出未來約 2,000～3,000 人同時在線的情境。目前尚未進行對應壓力測試，不能宣稱此原型已能穩定承載此規模。

同時在線人數不等於每秒登入數。各系統自己的 Cookie 有效時，多數操作由各系統驗證與授權，不需要每個請求都聯絡 SSO；本地登入失效才再次經 OIDC 驗證。SSO 尚有效時可省去重新驗證密碼，但仍有 Session、帳號、協定及資料庫處理成本。

以選課系統為例，SSO 可降低重複登入的負担，不能取代課程查詢、名額扣減、多人競爭與交易一致性的效能設計。正式上線需評估尖峰登入、重新驗證頻率、SQLite 並行寫入限制、資料庫選型及伺服器規格；多台 SSO 還需共用 Session 儲存、Data Protection 金鑰及持久 OIDC 簽章／加密金鑰。這些部署工作尚未實作。

## Cookie 被複製的風險

管理頁的登入紀錄 ID 不是登入憑證；但瀏覽器中仍有效的 SSO 登入 Cookie 若被竊取，可能被用來冒用該使用者進入其有權限的系統。伺服器端 Session 的優點是可撤銷，不能保證被複製的有效 Cookie 無法使用。各系統仍須檢查自己的功能權限。

持有有效 Cookie 的冒用者也可能觸發滑動續期，所以風險不能簡化為「最多 1 小時」。4 小時上限從原始登入起算，可限制中央登入的持續時間，但無法消除竊取風險。被竊的下游 Cookie 仍依各系統自己的期限及撤銷機制處理。

目前有 Secure／HttpOnly Cookie、伺服器端撤銷與期限檢查；尚未加入 MFA、敏感操作再次驗證、裝置綁定或異常風險判斷。這些可列入正式環境評估，不能將它們描述成既有功能。Cookie 被竊後，僅在最初登入做過 MFA 也不會自動讓該 Cookie 失效。
