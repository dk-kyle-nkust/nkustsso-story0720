# 串接系統與資料提供管理

## 使用方式

### 後台選單與管理權限

後台入口為 `/admin`，依目前帳號可用功能導向頁面。最高管理者在側邊「系統管理」可使用：

| 功能 | 網址 | 維護內容 |
| --- | --- | --- |
| 選單維護 | `/admin/menus` | 新增、編輯、刪除選單；設定名稱、分組、圖示、排序、啟用狀態與既有功能 |
| 權限管理 | `/admin/access` | 建立角色、勾選可用管理功能、指派帳號、停用角色及檢視異動紀錄 |

角色依功能授權，可分別授予 SSO／首頁連結、JSON／SOAP 串接、首頁分類、身分分類、登入管理、票券紀錄、開發進度與串接手冊。勾選功能名稱表示「查詢與維護」，另可勾選「僅查詢」；兩者都勾選時以維護授權為準。既有授權代碼保留維護語意，僅查詢使用 `功能代碼:read`。查詢角色可讀清單、紀錄與總覽，但不能開啟新增、編輯、撤銷表單，也不能 POST 異動；畫面同時隱藏維護入口。目前尚未將新增、修改、刪除拆成獨立權限。

帳號可加入多個角色，取得所有有效角色的權限聯集。角色編輯頁可搜尋已建立的帳號、加入或移除成員，儲存後生效。可設定角色授權開始與結束時間，畫面採臺灣時間，資料庫保存 UTC Unix 毫秒；留空表示該端不限。開始時間含該時刻，結束時間不含該時刻，每次請求重新判定。期限適用該角色全部成員，臨時代理可建立獨立的限期角色。既有角色升級時期限預設不限，不覆蓋既有權限或成員。

單位自動取得角色與資料範圍尚未實作，仍需確認所屬單位／工作單位的授權依據，以及要限制的資料類型。此版本沒有依單位自動授予權限。

尚未登入的校務人員在角色編輯頁的「加入校務人員」預先指派：輸入完整校務帳號查詢，核對姓名與校務身分後按「加入成員」，人員直接進入上方成員欄，再按「儲存角色」一併寫入。查詢與加入都在同一頁完成，不離開編輯頁，所以成員欄與權限勾選上還沒儲存的變更不會被丟掉。查詢使用 `LoginAuth` 唯讀來源，不讀取密碼；只有確認加入才在本系統建立無本機密碼的校務帳號。首次登入仍須通過原校務帳密驗證，沿用預先建立的帳號識別與角色。來源資料缺漏、不唯一、同名但來源不同、帳號停用或鎖定時會拒絕加入。此入口不授予最高管理者資格。

最高管理者沿用既有 `SsoAdministrator`，保留完整權限；此頁不修改、授予或撤除最高管理者資格。選單與權限管理只限最高管理者，兩個必要入口不可停用、改指其他功能或刪除。角色仍有成員時不能刪除，可先停用或清空成員。

最高管理者資格存在 Identity 的 `AspNetUserRoles`，和本頁維護的 `AdminRoleMembers` 是不同的表。因為這一頁本身就限最高管理者，**完全沒有最高管理者時整個後台無法進入**：導覽列篩不出任何選單、`/admin/*` 一律 403、入口首頁的後台連結也會隱藏。此時只能由技術端指派，見 [README 的「指派最高管理者」](../README.md)：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/grant-sso-administrator.ps1 -List
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/grant-sso-administrator.ps1 42665
```

`LoginSessionAdministration.Policy` 保留原名稱，由 `AdminAuthorizationService` 依實際控制器與資料庫授權判定；GET、POST 與舊網址別名均檢查，不能只靠隱藏導覽控制權限。每次請求重新查核帳號啟用／鎖定狀態、最高角色與一般角色，撤除成員或停用角色在下一次請求生效，不依賴 Cookie 中的舊角色。所有瀏覽器 POST 保留防偽檢查。

選單的啟用狀態只控制導覽，不撤銷功能權限。分組依組內最小排序值排列，組內依排序值、代碼排列。預設保留單一「串接系統管理」入口，SSO／首頁連結與 API 分頁依各自權限顯示；僅有 API 權限者會直接進入 API 分頁。新增選單只能選取既有功能，新增業務頁面仍須實作路由並加入 `AdminAuthorizationService.Features` 的固定功能對應，不能藉選單設定任意網址或授權規則。

設定保存在本系統資料庫（SQL Server 的 `NkustSSO`，或 SQLite 的 `sso.db`）的 `AdminMenus`、`AdminRoles`、`AdminRolePermissions`、`AdminRoleMembers`，不異動外部校務資料。首次遷移加入預設選單；每次啟動若 `AdminRoles` 完全沒有群組，會建立代碼及名稱均為 `admin` 的群組，預設啟用並授予八項一般後台功能的查詢與維護權限，不含最高管理者專用的選單與權限管理。群組預設沒有成員，也不建立帳號；若手動清空群組表留下同代碼的權限或成員關聯，重建前會清除這些殘留關聯。已有任一群組時不補建、不覆寫設定，也不還原撤除的權限；若刪除最後一個群組，下次啟動會再次建立空成員的 `admin`。重啟不還原已改名、停用或刪除的選單。最高管理者 `SsoAdministrator` 仍依原初始化邏輯建立，本機管理者帳號須另外設定。更新檢查 `Revision`，與 `AdminManagementAudits` 的變更前後快照同一交易提交。預先加入校務成員時，本機帳號的建立與其稽核在同一交易完成；成員關聯改由「儲存角色」一併寫入，所以加入成員不改角色版本，也不會蓋掉編輯頁上其他未儲存的變更。

驗證入口：`dotnet .local/admin-management-build/NkustSso.StorageChecks.dll --admin-management`、`tests/admin_management.py`。瀏覽器測試使用隔離資料，涵蓋實際分類維護、直接網址與 POST 越權拒絕、即時撤權、最高管理者保護、CSRF、舊表單衝突與桌面／手機 CSP 檢查。

校務成員驗證使用 `NkustSso.StorageChecks.dll --campus-role-members`（加 `--sqlserver` 使用隨機 SQL Server 測試庫），介面測試為 `tests/campus_role_members.py`，可透過 `NKUST_TEST_BUILD_DIRECTORY` 指定建置輸出。來源使用唯讀合成資料，不連真實校務庫或使用真實帳密。

角色分權與期限驗證為 `NkustSso.StorageChecks.dll --role-access`（同樣支援 `--sqlserver`）及 `tests/admin_role_access.py`，涵蓋直接網址與 POST 拒絕、時間邊界、多角色合併、舊結構升級、臺灣時間轉換及桌面／手機 CSP。

### 串接系統維護

重新建置並啟動更新後的 SSO。使用具備管理角色的帳號登入（本機管理者初始化見 [README](../README.md)），進入後台「串接系統管理」，或前往 `https://localhost:7100/admin/systems`。

管理入口統一為三個分頁，新增、編輯及密鑰頁也保留分頁導覽：

| 分頁 | 網址 | 管理內容 |
| --- | --- | --- |
| 首頁連結（預設） | `/admin/systems` 或 `/admin/systems?section=links` | 維護前台連結的名稱、分類、網址、排序與顯示專區 |
| 單一登入 SSO | `/admin/systems?section=sso` | OIDC、SAML 2.0、Web API 單一登入 |
| 帳密驗證 API | `/admin/systems/api?kind=new` | JSON 帳密驗證、SOAP 相容服務；保留「舊系統／新串接」分類 |

前台分類與服務連結由同一份資料庫設定產生。在首頁分類新增或改名，再於首頁連結選擇分類、勾選顯示專區與「在首頁顯示入口」，儲存後前台重新整理即可看到。取消「在首頁顯示入口」即下架；舊的前台入口網址也會拒絕轉址。`tests/portal_content.py` 以隔離資料驗證完整新增、修改及下架流程。

SSO 與首頁連結分別顯示清單、統計與異動紀錄，篩選及清除條件會留在原分頁。從首頁連結新增時預選連結，儲存後返回首頁連結分頁。舊 `/admin/integration-services` 及其新增、編輯、密鑰更新網址仍可使用，頁面內導覽採用新的 `/admin/systems/api` 路徑。

本次整合管理入口，不遷移或合併資料；SSO／連結沿用 `RegisteredSystems`，JSON／SOAP 沿用 `IntegrationClients` 及獨立服務授權。驗證端點、密鑰、來源 IP、回呼白名單及服務開關維持原規則，新增 API 登記不會建立首頁連結或中央登入。

清單將「入口顯示」與「開放身分」分成兩欄。「入口顯示」列出顯示／隱藏、專區及登入要求；「開放身分」顯示全部身分或指定身分，可展開查看完整群組條件，也可使用 DataTables 搜尋與欄位排序。此欄仍描述入口可見條件，不新增登入准入或業務授權。

### 後台介面

後台使用共用工作空間版型：桌面為側邊導覽，依「服務設定」「紀錄與維護」分組；手機以「選單」展開，支援 Escape 收合及鍵盤操作。上方顯示目前登入帳號與返回入口、登出操作。原「整合資訊」更名為「開發進度」，網址保留 `/integration`，使用後台版型；內容區分已實作、部分完成與待執行，不能把資料欄位完成當成資料匯入完成。

表格仍使用 DataTables 3.1.4，保留搜尋、排序及分頁。統一淺色表頭、列間距、狀態標籤、搜尋框與分頁樣式；單頁不顯示多餘分頁，空清單保留搜尋但隱藏筆數及分頁操作。手機的管理清單以欄位標籤呈現卡片，寬幅紀錄表則在表格範圍內捲動。串接服務的介面規格收在「介面與服務開關」展開區，清單優先呈現管理資料。

`_AdminLayout.cshtml` 統一架構，`admin-modern.css` 僅套用 `admin-workspace`，並在各頁樣式之後載入；`admin-shell.js` 負責手機導覽，`admin-ui.js` 負責表格及下拉。資源全部本機載入，前台不載入管理主題。`tests/admin_workspace.py` 驗證導覽、身分欄位、分類篩選、表格搜尋排序、鍵盤及不同寬度的版面與 CSP。

「Web API 單一登入」是本專案自訂的登入串接方式，不是標準協定名稱。接收系統須依本專案的核發／兌換接口完成串接；票券有短效期限，成功兌換後不能再次使用。「一次性票券」只指這個流程核發的登入憑證，不再作為另一個登入方式名稱。JSON 與表單兌換共用同一套系統登記及票券。

查詢分兩層：上方的下拉條件（登入方式、SSO 啟用狀態、首頁顯示／隱藏、首頁分類）在伺服器端決定結果集，保留在網址，可重新整理或收藏，按「清除條件」回到完整清單；表格本身的「表格內搜尋」由 DataTables 在前端即時過濾目前這份結果，並提供欄位排序與分頁。**關鍵字只有這一個入口**，不再有伺服器端的系統名稱／Client ID 查詢欄位，避免兩個搜尋框做同一件事。

下方異動紀錄同步篩選為目前符合下拉條件的系統；條件判斷依系統目前設定，並非異動當時的設定。

1. 新增系統，設定固定 Client ID、名稱、入口、登入方式、首頁分類、搜尋別名，以及精確的 HTTPS 回呼網址。
2. 勾選該系統確實需要的身分欄位。新系統預設只提供 `sub` 與協定必要資訊。
3. 儲存後取得獨立 Client Secret，只於建立成功頁顯示一次。交由接收系統後端保存，不放前端、網址、原始碼或一般日誌。
4. 接收系統完成登入轉向、回呼驗證、後端兌換及本地 Session／Cookie 建立。實作細節見 [SSO 系統串接流程書](sso-integration-guide.md)。
5. 登入 SSO 首頁，點選入口測試；首頁清單自動讀取設定，不必修改 Razor 連結。

登入方式包含 OIDC、Web API 單一登入、SAML 2.0 與「僅首頁連結（尚未串接 SSO）」。純連結只在入口列出網址，不接收登入，因此不需要回呼網址與密鑰，不會發出協定登入憑證；適合先把尚未串接的系統掛上入口。建立後不可改為其他方式，日後串接需另建正式系統登記。

### Web API 單一登入

在 `/admin/systems/new?section=sso` 選「Web API 單一登入」，填接收系統登入啟動頁、回呼網址，勾選可傳送的身分欄位。建立後顯示一次 Client Secret。新增／編輯及建立完成頁均有串接步驟。

這個選項使用現有 `ticket` 登記及核發流程，另提供真正接收 JSON 的 `POST /api/sso/v1/redeem`。不需要先串 OIDC；接收系統仍須實作 state／PKCE、回呼及本地登入，不能只填一個業務 API 網址就自動完成登入。既有票券系統、密鑰與表單兌換端點保持相容，不需資料庫遷移。

此功能與「帳密驗證 API」不同：使用者在中央輸入帳密，接收端只兌換短效票券，不取得使用者密碼。詳細參數及 JSON 範例見 [SSO 串接指南](sso-integration-guide.md#票券兌換-apijson)。隔離驗證入口為 `tests/webapi_sso.py`。

建立成功頁分為「串接資料」「提供的欄位」「串接指南與流程圖」：網址以「認證中心網址」「對方登入啟動網址」「對方登入回呼網址」標示，系統代碼與密鑰保留 Client ID／Client Secret 英文對照。密鑰只顯示一次，教學、流程圖與下載範例不包含真實密鑰。指南也可從既有系統編輯頁查看。

指南提供 [SVG 流程圖](../NkustSso.Server/wwwroot/guides/web-api-sso.svg)、[PNG 流程圖](../NkustSso.Server/wwwroot/guides/web-api-sso.png) 與 [HTTP 呼叫範例](../NkustSso.Server/wwwroot/guides/web-api-sso.http.txt)。JSON 回應範例依頁面載入時儲存的欄位授權產生，使用合成資料；它不是即時呼叫 API 或正式資料。HTTP 檔只示範格式，對方仍須實作 state／PKCE、回呼關聯驗證與自己的登入狀態。流程圖來源為 `web-api-sso.mmd`，以 `python scripts/render-web-api-guide.py` 重新產生。

SAML 系統另外填寫 SP Entity ID 與 SP 簽章公開憑證（PEM）；登入回呼填 ACS，首頁入口填 SP 的 SAML 登入啟動網址。把 `/saml/metadata` 交給對方設定 IdP 信任，不產生共用 Client Secret。本站要求 RSA-SHA256 簽章的 HTTP-Redirect AuthnRequest，回傳簽章的 HTTP-POST Response／Assertion。NameID 使用固定帳號 ID；可選 Attribute 沿用欄位清單的名稱與白名單。綁定方式與目前限制見 [README 的 SAML 接入說明](../README.md#saml-20-接入)。

首頁分類與搜尋別名只影響入口首頁的呈現與尋找，不影響任何授權。分類由資料庫管理，首頁依分類分區顯示。搜尋別名以空白分隔，填使用者慣用的說法，例如「經費結報簽核」加上「報帳 核銷 差旅」，輸入「報帳」才找得到。設計理由見 [入口首頁：系統很多時怎麼呈現](portal-design.md)。

## 首頁分類與排序

### 功能詳述與顯示順序

在系統編輯頁填寫「功能詳述」（最多 300 字），公開專區會在滑鼠移入、鍵盤聚焦或點擊說明按鈕時顯示；留空則不顯示提示。此內容儲存於 `RegisteredSystems.Description`，也參與專區搜尋與顯示。

系統編輯頁另有「英文系統名稱」（最多 100 字）與「英文功能詳述」（最多 600 字）；分類編輯頁有「英文分類名稱」（最多 100 字）。分別存入 `RegisteredSystems.DisplayNameEn`、`RegisteredSystems.DescriptionEn`、`PortalCategories.NameEn`。英文版優先顯示這些欄位，未填則使用既有名稱譯文或保留中文原文；請補齊自行新增服務的英文內容。前台搜尋同時涵蓋中英文，存檔後重新整理即生效，排序與公開專區設定共用。英文內容沿用既有權限、版本檢查與異動稽核。

「首頁排序（分類內）」控制同一分類的項目順序，數字越小越前面；不同分類區塊的先後則到「首頁分類管理」調整「分類排序」。可用 10、20、30 預留插入空間。兩者都是跨專區共用設定，儲存後重新整理公開目錄即可看到變更。

### 未登入的公開專區

系統編輯頁的「顯示專區與隱私」可分別勾選學生、教職員、校友；教師與職員共用教職員專區。未勾選「登入後才顯示」的公開項目，任何訪客都能看到該服務的名稱、說明、分類與搜尋別名，勾選「登入後才顯示」（`RequireLoginToView`）後，該入口的名稱與說明只對登入且符合身分條件者顯示。沒有指定任何專區的既有私人入口仍只在登入且符合身分條件後，顯示於各專區。新登記預設不公開；取消「在首頁顯示入口」會連同公開目錄一起隱藏。停用 SSO 系統也會立即撤下公開入口。

點選服務一律另開分頁，需登入時在該分頁完成登入並接續服務，原選單保留。訪客可直接瀏覽 `/portal/student` 等專區；點選 SSO 服務才進入中央登入，成功後接續前往該系統。入口網址應填接收系統的 SSO 登入啟動網址，不能只填原本獨立的帳密頁。外部純連結預設直接開啟；勾選「開啟服務前的登入要求 → 需先登入本站」後，未登入者先到統一登入頁，有效登入期間內沿用本站 Session。此欄位為 `RegisteredSystems.RequirePortalLogin`，可在編輯頁勾選或取消並儲存；不會變更協定或替外部網站建立登入狀態。分類與專區都不授予業務權限，接收系統仍須自行驗證與授權。

首次升級會匯入校方公開指南的服務連結，全部以純連結設定，不宣稱已串接 SSO。已隱藏、改成其他網址或原本為 SSO 的同名登記不會自動公開。此初始化只執行一次，後續修改、取消發布與刪除由管理者決定，重啟不還原。

### 共用分類

管理者可前往 `/admin/categories`（導覽列「首頁分類管理」），新增或編輯分類代碼、名稱、顏色與排序。代碼建立後固定，名稱可修改；`all` 是首頁篩選保留字，不能作為新分類代碼。顏色從既有配色選擇。

- 首頁先依「分類排序」排列，再依每個系統的「首頁排序（分類內）」排列；數字越小越前面，同值依分類代碼或 Client ID 排列。建議使用 10、20、30 等間隔。
- 系統管理新增「首頁分類」查詢條件與列表欄位，可和關鍵字、登入方式、SSO 狀態及首頁顯示條件組合查詢。分類清單的系統數可直接連到所屬系統。
- 分類若仍有系統使用（包含停用及隱藏系統），不能刪除；請先編輯那些系統，改選其他分類。`general` 是兜底分類，可更名與排序，但不能刪除。
- 沒有符合使用者身分之可見入口的分類，不顯示在該使用者首頁。首頁已移除「顯示其他身分」功能，`?all=true` 也不能略過身分限制；舊個人首頁、常用及最近使用已移除，登入前後皆使用同一套專區介面。
- 分類儲存後，首頁重新整理即套用，不需重啟或重新登入。分類有版本檢查，避免舊表單覆蓋新設定；新增、修改、刪除都會記錄管理者、時間、IP 及前後資料。

首次啟動新版時，linq2db 會建立 `PortalCategories`、`PortalCategoryAudits` 及 `SchemaMigrations`。一次性遷移保留原有九類與順序，既有非空自訂分類代碼會建立同名分類，空分類歸入 `general`。重啟不會還原管理者修改或刪除的分類。無須手動重建資料庫。

Client ID 與協定建立後不可修改；登入回呼、登出回呼、顯示名稱、說明、排序、欄位與狀態可編輯。OIDC 登出回呼不表示已完成全系統同步登出。Web API 單一登入不填此欄。

管理頁目前沒有密鑰查閱／輪替功能；離開新增成功頁後無法取得原始密鑰。正式上線前須補齊密鑰輪替及安全交付流程。新增 OIDC 客戶端仍由 OpenIddict 管理雜湊與驗證。

## 欄位授權

| 欄位 | OIDC claim | Web API 單一登入 JSON |
| --- | --- | --- |
| 固定使用者識別碼（必要） | sub | sub |
| 校園帳號 | preferred_username | username |
| 使用者姓名 | name | name |
| 校園身分類型 | identity_type | identity_type |
| 班級代碼／名稱 | class_code / class_name | 同左 |
| 學籍狀態代碼／名稱 | student_status_code / student_status_name | 同左 |
| 學制代碼／名稱 | education_level_code / education_level_name | 同左 |

以上調整的是後台中文標示，英文回傳鍵值及欄位授權維持現有契約；例如 Web API 的校園帳號仍為 `username`，使用者姓名仍為 `name`。

上述可選欄位可各自勾選。此版本不開放任意 SQL 欄位或自訂欄位名稱，不提供密碼、Security Stamp、中央 Session 識別值、管理者角色。若未來新增可提供欄位，必須明確加入後端白名單並評估必要性。

OIDC 須同時符合用戶端要求的 scope 與管理者欄位白名單：帳號／姓名要求 `profile`，其餘身分資料要求 `student_profile`。只要求 scope 不會取得未勾選的欄位。授權碼核發與兌換時均重新套用限制。必要的 issuer、audience、到期等協定資訊不受可選欄位勾選影響。

票券在後端兌換時重新讀取目前設定；未允許的欄位直接省略，不傳空字串假裝有資料。既有的 IncludeStudentProfile 限制也仍生效。接收端須處理欄位缺少的情況，不應把缺少資料視為具有功能權限。

## 狀態與撤銷

### 首頁入口可見身分

身分規則套用於「登入後才顯示」的私人入口，以及未勾選任何公開專區的既有私人入口。公開顯示名稱的服務不使用這組規則隱藏名稱；是否需要登入由協定與「需先登入本站」設定決定。

每個系統的新增／編輯頁，以身分群組卡片設定開放範圍。學生可依學籍狀態、部別、學制等逐步細分；教職員可依教師／一般職員、任職狀態、任用類別等設定。共用條件與選項可在 `/admin/identity-catalog` 查詢（唯讀，資料由校務資料庫提供），種類由系統預先定義，不提供後台新增種類；各種類未來可對應各自資料庫來源，目前來源設定與同步尚待串接。操作與來源介面詳見 [身分分類與群組規則](identity-audiences.md)。

- 條件明確選擇「全部／指定」，指定模式清空勾選會阻止儲存。同條件選項採 OR，同組條件採 AND，不同組採 OR。
- 例如「學生＋在校＋日間部」是一組，「現職教師」可以是另一組；符合其中一組即可。
- 同一帳號可有多筆身分，每組必須由同一筆身分完整符合，不可跨身分拼湊。缺少資料不能符合已指定條件；管理者不自動例外。
- 全域選擇「全部身分」時，所有已登入使用者適用。既有系統未設定規則時維持原行為。
- 專區每次讀取最新身分及分類後判斷；後端不把私人入口的名稱、詳述或連結傳給未登入或不符合身分的使用者。點選私人入口時也會重新檢查，無權限回傳 404。系統停用或全體首頁隱藏的設定優先，不會因身分符合而顯示。
- 此功能只控制入口顯示，不限制 OIDC／Web API 單一登入／SAML 登入，不取代各系統後端授權。若要拒絕某些身分透過 SSO 登入，需另設計登入准入規則。

`PortalAudiences.RulesJson` 保存版本 2 分組規則；沿用 linq2db，新版自動補欄位並相容舊三類規則。共用分類及多重身分另建資料表。未串接來源的帳號以現有帳號資料形成一筆身分；正式同步來源仍待接入。規則與系統設定在同一交易儲存，共用版本衝突保護；異動稽核保存前後規則，重新啟動不重設。與「允許提供的身分欄位」分開：判斷入口可以使用某項資料，並不表示會把該資料傳給接收系統。

- 「首頁顯示」只控制入口顯示，隱藏後仍可直接到該系統發起登入。
- 「啟用 SSO 登入」控制新的 OIDC 授權／兌換與票券核發／兌換。停用後，不允許新登入；已核發但尚未兌換的票券／授權碼也在兌換時檢查狀態。
- 不會遠端清除各系統已建立的 Cookie，也無法回收對方先前保存的資料。更新前已通過檢查的進行中請求可能完成。
- 各系統的功能權限仍由各系統後端執行。接收系統自行設定本地登入期限；中央登入滑動 1 小時、絕對上限 4 小時。

## 資料與稽核

使用 linq2db，在 `sso.db` 新增 `RegisteredSystems` 與 `SystemConfigurationAudits`。不使用 EF、不刪除既有帳號或協定資料。

啟動不再新增示範登記，也不覆蓋已儲存的密鑰、回呼與欄位設定。新系統預設額外欄位皆不勾選；既有示範入口若不再使用，可停用並取消首頁顯示。

設定異動保存管理者固定 ID、時間、連線來源 IP 與變更前後設定；不保存原始密鑰。管理頁顯示最近 30 筆。異動稽核目前沒有自動清除規則，正式環境須訂定保存期限與存取／備份政策。位於反向代理後方時，必須先設定可信任代理，不能直接相信任意 X-Forwarded-For。

編輯使用版本欄位避免舊頁面覆蓋新設定；既有系統的公開協定設定、欄位政策與稽核在同一個資料庫交易更新。新增 OIDC 先由 OpenIddict 建立機密紀錄，在管理登記完成前無法登入；正常失敗會清理新建紀錄。若程序在新增中途終止，可能留下尚未管理登記的 OIDC 紀錄，仍會拒絕登入，須由維運確認並清理。

## 正式環境與資料外洩

SSO 不必複製一份正式帳密資料庫。可以串接既有帳號來源，保留固定使用者 ID，另存 SSO 管理角色對應、Session、串接系統與稽核。`AspNetUsers` 保存本機帳號或校務來源識別快照，`AspNetRoles` 與 `AspNetUserRoles` 保存本地管理角色；校務來源密碼不會複製到本機。正式切換仍須確認驗證與角色／身分對應，不能只改資料表名稱。

管理介面完成不代表整個原型已可正式部署。Development 限制、正式帳號來源、正式憑證、持久 OIDC 金鑰、資料庫容量、備份及密鑰輪替仍需完成部署設計。

採最小資料提供原則。HTTPS 保護傳輸，無法防止接收端遭入侵或資料被誤存、誤用。接收端應限制資料存取及保存期限，避免記錄完整 Token、票券、Cookie、密鑰或不必要的個資。取消欄位授權僅影響後續提供，不能回收已傳出的資料。

## 驗證

`python tests/systems.py` 會建立獨立資料庫、臨時 HTTPS 連接埠及瀏覽器，驗證管理權限、CSRF、兩種方式的欄位限制、停用、回呼白名單、重放、版本衝突、設定保存及稽核不含密鑰，結束後停止自己的測試服務。

可將伺服器 DLL 路徑作為第一個參數，以測試獨立建置輸出。`Sso:DataDirectory` 可指定本機開發資料目錄，預設仍為工作區 `.local`；勿將正式機密目錄作為測試目錄。


## JSON API／SOAP 串接服務維護（2026-10-16）

管理者從後台側欄「串接系統管理」切換到「帳密驗證 API → 新串接」（`/admin/systems/api?kind=new`），點「新增串接系統」。JSON／SOAP 使用實際驗證端點讀取的 IntegrationClients，與同一管理入口中的 SSO／首頁連結保留各自資料與授權。

1. 填寫系統代碼、名稱，選 JSON API 或 SOAP 相容服務。
2. 填寫接收系統主機的允許來源 IP，每行一個完整 IPv4／IPv6；不接受萬用字元或網段。
3. 在「可使用的服務」勾選需要的「帳密驗證」，再勾選「啟用此串接」後儲存。個別用戶端開放狀態與服務資格可隨時修改，不須重啟服務。
4. JSON 建立後顯示一次密鑰，交由對方保存在伺服器設定。之後可從列表「更新密鑰」產生新值；舊密鑰立即無法通過新的請求驗證。
5. SOAP 保留舊方法參數，使用來源 IP 識別用戶端，不加額外密鑰參數。同一 IP 不能重複對應不同的已啟用 SOAP 用戶端。

管理列表同時顯示「個別用戶端」與「服務總開關」的實際狀態：停用、等待服務開啟或已啟用。部署端需先完成驗證來源設定並啟用 `IntegrationServices:JsonEnabled`／`SoapEnabled`；此後新增相同介面的接收系統只需後台登記。後台新增用戶端不會自行新增 API 方法或改變 WSDL。

| 介面 | 實際入口 | 授權 |
| --- | --- | --- |
| JSON | POST /api/integration/v1/verify | 來源 IP + X-Client-Id + X-Client-Secret |
| SOAP 1.1／1.2 | /KuasSSOWebService.asmx | 來源 IP；規格可從 ?wsdl 查閱 |

目前 JSON 回傳帳密驗證結果，不提供個人資料；SOAP 目前提供 `KuasSSO_Certify2` 相容方法，其餘舊方法尚未開放。若未來新增其他 API 功能或個人資料欄位，仍須實作對應端點及授權規則，不能只新增一筆管理資料便取得新功能。帳密驗證介面也不等於瀏覽器 SSO；接收系統自行管理登入狀態。

管理頁沿用 ManageSessions 授權及 POST 防偽保護；Revision 防止舊表單覆蓋新設定。IntegrationClientRegistrationService 與實際端點共用同一份登記；IntegrationAudits 保存設定異動，不含使用者帳密、系統密鑰或其雜湊。密鑰頁回應設為 no-store。

驗證：`tests/service_integrations.py` 測試管理新增／編輯、開關、IP 驗證、密鑰更換、版本衝突、權限、CSRF、RWD 與 CSP；`IntegrationVerificationChecks` 測試實際用戶端授權、停用、密鑰輪替與 SOAP 契約。測試使用隔離資料庫，不連線正式帳號來源。


### 串接服務的聯絡資訊與詳細備註

串接服務提供「舊系統」與「新串接」兩個分頁，分開顯示系統及最近紀錄。舊系統用於保留對方現有規格；新串接預選共用 JSON 驗證介面。新增時帶入所在分類，也可於編輯頁調整「串接分類」；此設定不變更協定或授權。升級前已登記的資料先歸入舊系統，並保留原設定。詳細行為見 [分頁與分類說明](integration-services.md#舊系統與新串接)。

新增／編輯頁提供獨立的申請人、承辦人、聯絡電話與電子郵件欄位。姓名與電話最多 100 字，電話可包含分機；電子郵件最多 254 字並檢查格式。欄位可依情況選填，管理列表直接顯示聯絡窗口，並可使用表格搜尋姓名、電話或郵件。資訊僅供後台管理者查看，修改沿用版本檢查與異動稽核。

新增／編輯串接系統時，可於「詳細備註」填寫最多 20,000 字的純文字，保留換行。建議記錄系統用途、負責單位、聯絡窗口、維護廠商、規格文件位置、參數／回傳說明、測試與驗收結果、上線日期及交接事項。可留空或清除；不要填入密碼、密鑰或真實帳密測試資料。

內容儲存在 IntegrationClients.Notes；舊資料庫啟動時自動補欄位，既有備註預設空白，不變更授權設定。管理列表可展開「查看備註」，既有表格搜尋也能搜尋備註。新增與修改沿用版本檢查及異動稽核，保留修改前後內容。備註只在管理後台顯示，不發布到公開首頁、JSON 回應或 SOAP WSDL；HTML 與腳本以文字顯示，不執行。

### 系統資料、來源對應與服務授權

在 `/admin/systems/api` 的新增／編輯頁維護以下資料，列表也能搜尋用途、負責單位及來源識別。

| 畫面欄位 | 儲存欄位 | 規則 |
| --- | --- | --- |
| 系統用途 | IntegrationClients.Purpose | 選填，最多 1,000 字，與詳細備註分開 |
| 負責單位 | IntegrationClients.OwningUnit | 選填，最多 100 字 |
| 來源系統 | IntegrationClients.SourceSystem | 最多 100 字，與原識別碼一起填寫或一起留空 |
| 原系統識別碼 | IntegrationClients.SourceId | 最多 100 字，保留大小寫，與來源系統組成唯一對應 |
| 匯入批次 | IntegrationClients.ImportBatchId | 唯讀，由移轉程序寫入；一般新增留空 |
| 匯入時間 | IntegrationClients.ImportedAt | 唯讀，UTC Unix 毫秒，未匯入為 NULL |
| 可使用的服務 | IntegrationClientServices | 每個系統與每項服務一筆關聯，不存於備註 |

`IntegrationCapabilities` 保存服務識別與名稱；目前可授權 `account.verify`（帳密驗證），適用於現有 SOAP 與 JSON 驗證介面。新增串接預設不勾選服務，未授權時即使啟用、IP 與密鑰正確，仍會拒絕呼叫。管理頁會顯示「未授權服務」。取消勾選後儲存立即影響後續授權檢查；已通過檢查的進行中請求可能完成。服務資格與接收系統內的使用者權限無關。

新增服務需要對應程式實作、明確的端點授權檢查及測試，不能只新增資料列就開放新功能。目前介面不提供任意新增服務的功能。

新版啟動時自動補欄位、建立服務與關聯資料表，並以一次性遷移保留既有串接的帳密驗證資格；原本停用的仍停用，密鑰及其他資料不變。管理者後續取消的服務資格不會因重新啟動恢復。一般編輯不能覆寫匯入批次、時間；用途、單位、來源對應與服務授權的修改，在同一交易套用版本檢查並記錄異動。來源唯一索引避免同一來源資料重複登記。

這次只補齊後台欄位與授權關聯，尚未執行來源資料匯入，也不會把升級時間當成匯入時間。正式移轉時需確認來源的帳號、系統與服務關係，逐筆對應後再記錄批次；不得將不同服務全部視為帳密驗證或複製明文密碼。這些管理資料只供後台使用，不新增公開個人資料回傳。

驗證涵蓋既有資料升級、重複來源、長度與配對檢查、服務增撤、重啟保留、版本衝突、匯入欄位保留與異動稽核；瀏覽器另驗證欄位保存、錯誤回填、勾選取消、桌面／手機與 CSP。


### 後台與前台共用風格

後台與前台共用 clean-layout.css 的配色變數、按鈕、卡片、鍵盤焦點與減少動態效果設定。頁首使用相同的高科大橫式校名圖、金色頂線與淺色導覽；保留管理頁較寬的表格空間，手機上功能導覽可橫向捲動，登入者與登出維持靠右。DataTables／Tom Select 依同一組色彩與圓角呈現，無需放寬 CSP。

## 串接手冊下載

後台「串接手冊」位於 `/admin/manuals`，提供 16 份 PDF 與整包 ZIP。最高管理者可使用；其他人員由權限管理授予 `manuals` 或 `manuals:read`，兩者均可瀏覽及下載。未登入導向登入，登入但未授權則拒絕；撤權立即影響後續請求。

PDF、ZIP 與固定清單嵌入組件，由控制器核對手冊代碼後回傳，沒有公開靜態檔案路徑；每次下載重新檢查權限並禁止快取。桌面可搜尋手冊名稱及 SOAP 方法，手機使用卡片排列。

首次升級以 `admin-manuals-v1` 補上選單，不擴張既有群組權限，之後保留管理者對選單的排序、停用與刪除。更新手冊需先執行 `python docs/developer-integration/generate.py` 再編譯網站；文件來源、產生清單與 PDF 一起版本管理。
