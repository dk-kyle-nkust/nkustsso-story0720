# SSO 身分資料需求

SSO 登入成功後，需能向已整合的系統提供共用身分資料，供各系統依自己的授權規則判斷可使用的功能。

## 已確認架構需求

- 使用 ASP.NET Core；資料存取採 linq2db，不使用 Entity Framework。
- 中央採伺服器端 Session，瀏覽器以安全 Cookie 攜帶 Session 參照。
- 管理者可查詢及終止單筆或同帳號全部中央登入，操作需留存原因與紀錄。
- Server 不建立固定測試帳號；全新本機管理者須透過設定明確建立，既有帳號及角色不覆寫。
- 在學、休學、停用與管理者帳號只作為隔離測試資料，不隨 Server 啟動注入。
- 班級、學籍身分與學制由 SSO 提供；各系統仍自行控管功能權限。
- 管理者在 `/admin/systems` 新增／編輯／停用 OIDC 或 Web API 單一登入串接；首頁讀取登記設定。
- 每個系統可依身分類型、學籍狀態、學制設定首頁入口可見條件；同類 OR、跨類 AND、未設定的類別不限。首頁顯示不等於登入准入或功能授權，既有系統預設維持所有身分適用。
- 每個接收系統使用獨立 Client ID；OIDC／Web API 單一登入使用密鑰，SAML 使用 Entity ID 與簽章憑證建立信任。可逐一允許帳號、姓名、身分類型、班級、學籍身分及學制代號／名稱；新系統預設只提供固定識別碼與協定必要資訊，各協定均由後端強制過濾。詳見 [串接管理](system-administration.md)。
- 正式 SSO 可沿用既有帳號來源，不必複製帳密；管理資格另以固定使用者 ID 對應角色。現有本機帳號需在正式串接時替換驗證與對應程式。
- 目前中央撤銷不會立即撤銷下游系統 Cookie；全系統即時登出需另串接通知或中央狀態檢查。
- 續期方案須兼顧資訊安全、使用便利及各系統最小改動。目前已加入中央 1 小時滑動續期，最長連續登入依使用者更正為 4 小時，沿用既有 OIDC 導向。詳細行為、限制及正式環境待辦見 [SSO 登入續期與系統整合需求](sso-session-renewal.md)。

## 已確認新增欄位

| 欄位 | 意義與範例 | 待確認事項 |
| --- | --- | --- |
| 班級 | 使用者所屬班級 | 傳送班級代號、名稱或兩者；實際資料來源 |
| 身分代號 | 學籍狀態，例如在學、休學 | 實際代碼值、完整狀態清單及資料來源 |
| 學制代號 | 學制，例如碩士班、大學部 | 實際代碼值、完整學制清單及資料來源 |

「身分代號」在此指在學、休學等學籍狀態，與學生、教師、職員等身分類別分開定義。範例不是完整的代碼清單，尚未指定數字或英文代碼。

## 後續介面設計

- 確認上述欄位對應的資料庫欄位或既有服務，以及對外傳送的欄位名稱。
- 確認非學生或資料缺漏時，各欄位應如何表示。
- 確認學籍狀態或班級異動後，SSO 提供的資料多久更新。
- 各系統驗證 SSO 身分結果後，依自身規則使用這些資料；共用身分資料不直接取代系統內的細部權限。

## 身分分類與開放範圍（首頁範圍已實作）

### 已確認原則

- 後台依身分類別與群體條件設定開放範圍，可逐層增加限制。
- 不設定到個人，不提供個人白名單、黑名單或例外授權。
- 同一帳號可以同時具有多筆身分，不強迫只選一個主要身分。
- 系統自動逐筆比對身分；只要任一筆身分完整符合任一組開放條件，即符合開放規則。
- 同一組內的不同條件必須全部符合；同一條件可選多個值，符合其中一值即可；不同組之間符合任一組即可。
- 不可把不同身分的欄位混合，拼湊成符合條件的身分。
- 管理畫面顯示身分分類、條件與開放範圍摘要，不需列出個人名單或輸入個別測試帳號。

### 分類與畫面設計方向

使用者希望由身分逐層細分：學生可分在校、休學、退學、畢業，再依日間／夜間等條件細分；教職員也需涵蓋教師、一般職員、公務人員等身分。分類名稱與代碼須依校方正式資料確認，不把以下例子視為既定人事分類。

建議把「身分分類維護」與「各系統開放範圍」分成兩個管理工作：前者定義身分類別、可用條件與資料來源；後者只選擇哪些人能使用該系統。一般管理者不應在每個系統重建分類，也不直接填寫條件程式。

後續確認：種類由系統預先定義，後台移除「新增種類」，需要新種類時由技術端擴充。每個種類未來可有各自的資料庫來源，來源提供該種類的選項，管理重點改為來源對應與同步狀態。分類選項來源與使用者身分來源分開，以固定代碼關聯。目前已移除新增種類功能；來源連線、欄位映射及同步排程仍待串接。

使用者確認不需細分到個人：開放範圍只設定身分類別與群體條件，不提供個人白名單、黑名單或例外授權；畫面不需輸入個別測試帳號。這不限制帳號的身分數量，同一帳號仍可同時具有多筆身分，由系統依來源資料自動比對。

| 大類 | 可展開的條件範例 |
| --- | --- |
| 學生 | 學籍狀態 → 部別（日間／進修等）→ 學制 → 校區、學院／系所、年級 |
| 教職員 | 類別（教師／行政職員等）→ 任職狀態 → 聘任／任用類別 → 校區、單位 |
| 其他 | 依資料來源登記訪客、外部合作人員等；未定義身分不可自行推定為學生或教職員 |

畫面採「身分群組卡片」，預設收合顯示摘要。選擇學生後出現學生條件；選擇教師或職員後出現相應條件。每一層都有明確的「全部／指定」選擇，指定模式必須至少選一項；清空勾選不等於開放全部。更細條件以「新增限制」展開，常見畫面不一次攤開整棵樹。選項多時提供搜尋、已選標籤及階層路徑，手機以單欄卡片呈現。

「在校／日間部／大學部」與「畢業／不限部別」應是兩組獨立規則，避免同一個日夜間條件錯誤套用到所有學籍狀態。學生與教師規則也各自保存。每組內的條件全部符合，任一組符合即可。儲存前用白話顯示例如「在校的日間部大學部學生，或現職專任教師」，讓管理者確認開放條件，不列出個人名單。

資料模型須允許一人多筆身分，例如在職進修職員、兼任助理的學生；每筆身分分別帶有學籍／任職狀態、單位與有效期間。判斷一組規則時，所有條件必須符合同一筆身分，不能把不同身分的欄位拼湊成符合。教師、行政職員、公務人員資格與專任／兼任的實際關係依人事來源映射，不硬套為互斥的單一階層。缺漏資料不符合已指定的條件，來源中斷也不能自動放寬範圍。

### 多重身分判斷範例

同一帳號同時具有「現職行政職員」與「在校、夜間部、碩士班學生」兩筆身分時：

| 系統開放條件 | 判斷結果 |
| --- | --- |
| 現職職員 | 符合，由職員身分滿足條件 |
| 在校且夜間部的學生 | 符合，由學生身分完整滿足條件 |
| 在校且日間部的學生 | 不符合，該學生身分為夜間部 |
| 現職教師 | 不符合，職員身分不自動視為教師 |
| 現職職員，或在校日間部學生 | 符合，職員身分已滿足其中一組 |

即使同一帳號另有多筆學生身分，也要逐筆完整比對。例如「在校、夜間部」與「畢業、日間部」兩筆身分，不能合併判定為「在校、日間部」。這些例子只用於說明規則，後台不建立個人例外設定。

### 分類維護與後續確認

分類使用穩定代碼；改顯示名稱不改既有規則。分類停用仍保留既有規則與異動紀錄，不能因刪除選項變成不限。明確選擇「全部」代表涵蓋該條件日後新增的值；「指定」只涵蓋已選代碼，畫面需清楚提示此差異。常用範圍可先提供可複製的範本，避免直接引用會隨範本編輯而連動變更權限。

**本次實作：** `/admin/identity-catalog` 查詢共用條件與選項（唯讀，不提供新增或編輯），`/admin/systems` 以群組卡片設定首頁範圍，支援複製群組、漸進新增條件及即時摘要。已完成多重身分資料模型、有效期限判斷、完整快照同步服務及舊規則相容；不提供個人例外設定。詳細操作與同步介面見 [身分分類與群組規則](identity-audiences.md)。

**待確認：** 是否進一步控制 SSO 登入准入，以及正式身分類別、層級、代碼與學籍／人事資料來源。目前仍只控制首頁入口可見性；正式來源連線與欄位映射尚未接上，既有帳號沿用原單一身分資料，缺少的部別／任用類別不會自行推定。如果擴充為登入准入，OIDC、Web API 單一登入與 SAML 核發／兌換都必須套用同一規則，不能只在首頁隱藏連結。下游系統內部功能權限仍由各系統管理。

身分可為多值的方向也符合 [REFEDS eduPersonAffiliation](https://wiki.refeds.org/display/STAN/eduPerson%2B%28202208%29%2Bv4.4.0) 的模型；本地的細部學籍、人事分類仍須另行定義。

## 原型欄位對應

| 需求 | 原型代號欄位 | 原型名稱欄位 |
| --- | --- | --- |
| 班級 | `class_code` | `class_name` |
| 身分代號 | `student_status_code` | `student_status_name` |
| 學制代號 | `education_level_code` | `education_level_name` |

原型使用 `student_profile` OIDC Scope 傳遞上述欄位。代碼採用 `DEMO_` 或 `DEMO-` 前綴，僅供驗證流程；正式代碼尚未指定。班級名稱與代號先同時提供，待資料來源確認後調整。執行方式與整合界線見專案根目錄的 README.md。
