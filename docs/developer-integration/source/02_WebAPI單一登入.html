對方需準備兩個瀏覽器入口：登入啟動頁及回呼頁；再由對方後端呼叫中央兌換 API。中央不會拿使用者帳密 POST 到對方網站。

申請設定

  • 提供精確登入啟動網址與回呼網址；取得 Client ID、一次顯示的 Client Secret 與 SSO 基底網址。
  • 請管理者在 SSO 系統設定選「Web API 單一登入」，啟用系統並勾選允許提供的身分欄位。
  • Client Secret 與 verifier 只保存在接收系統後端；回呼完成清除登入請求並轉到不含 ticket 的網址。
本文件為目前開發版介面規格；正式網址、系統代碼、密鑰／憑證、授權欄位與測試帳號請向 SSO 管理者取得。example.edu 為示意位址，不可直接呼叫。

登入啟動與回呼：語言中立示意

startLogin(browserSession):
    state = base64url(randomBytes(32))
    verifier = base64url(randomBytes(32))
    challenge = base64url(SHA256(ASCII(verifier)))
    savePending(browserSession, state, verifier, shortExpiry)
    redirect(SSO + "/ticket/authorize?" + urlEncode({
        client_id: CLIENT_ID, redirect_uri: CALLBACK,
        state: state, code_challenge: challenge,
        code_challenge_method: "S256" }))

callback(browserSession, ticket, state):
    pending = atomicallyTakePending(browserSession, state)
    require(pending exists and not expired)
    data = backendPostJson(SSO + "/api/sso/v1/redeem",
        basicAuth(CLIENT_ID, SECRET), {
        ticket: ticket, redirect_uri: CALLBACK,
        code_verifier: pending.verifier })
    require(HTTP == 200 and validJsonSchema(data))
    require(data.issuer == EXPECTED_ISSUER)
    require(data.client_id == CLIENT_ID and data.sub != "")
    require(data.session_expires_at > nowUnixSeconds())
    account = requireEnabledLocalAccount(data.issuer, data.sub)
    createLocalSession(account, min(localExpiry, data.session_expires_at))
    redirectToAllowedLocalPage()

base64url 使用 -、_ 並移除 =。每次登入都產生新的隨機值；多分頁以 state 分別保存，不覆蓋同一筆 verifier。原子取出失敗、兌換逾時或重複回呼時，重新發起登入，不能把舊票券當成功。

HTTP 兌換範例

POST /api/sso/v1/redeem HTTP/1.1
Host: sso.example.edu
Authorization: Basic BASE64_OF_CLIENT_ID_COLON_SECRET
Content-Type: application/json

{"ticket":"CALLBACK_TICKET", "redirect_uri":"https://app.example.edu/sso/callback",
 "code_verifier":"SAVED_VERIFIER"}
範例字串均為占位符，不符合正式票券長度；需代入當次實際值。JSON 兌換端點與舊表單 /ticket/redeem 共用一次性消耗狀態，不能各兌換一次。

回應範例及失敗處理

{
  "issuer": "https://sso.example.edu/",
  "client_id": "YOUR_CLIENT_ID",
  "sub": "stable-user-id",
  "authenticated_at": 1792368000,
  "session_expires_at": 1792369800,
  "username": "S000001",
  "name": "測試學生",
  "identity_type": "student"
}

時間與人員資料均為示意；username、name、identity_type 只有被授權才提供。驗證依賴與受信任中央的 HTTPS 後端通訊，這個 JSON 本身不是簽章 JWT。

情境處理
400 invalid_request檢查欄位、字元及長度；不要無限重送。
400 invalid_client_or_redirect授權入口的系統未啟用或回呼不符；核對登記。
400 session_inactive中央登入不可用；重新發起登入。
401 invalid_client後端兌換的系統驗證失敗；核對 ID／密鑰。
400 invalid_ticket逾時、重放、verifier／回呼不符或登入已失效；重新登入。
413／415／網路或服務錯誤請求上限 8 KiB；使用 application/json，非 200 一律不建立登入。

驗收重點

  • 正常登入、中央已登入與登入逾時三種情境都要測試。
  • 錯誤回呼、錯誤密鑰／簽章、票券重放、停用系統與停用帳號必須拒絕。
  • 只有允許的欄位才可使用；欄位缺少或空白要能處理。
  • 本地帳號未開通或沒有業務權限時顯示拒絕頁，不自動授予管理權。
  • 登入後導向不含 code／ticket 的站內頁面；日誌不留原始密鑰、票券或 Token。
中央與接收系統各自建立 Cookie／Session。中央登入有效可省略再次輸入帳密；接收系統仍須完成驗證。中央登出不等於所有下游同時登出，本版未實作完整跨系統單一登出。
